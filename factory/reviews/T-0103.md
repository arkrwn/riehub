## Secrets and content

- [x] S1. Every new stored field that holds a credential or user content is encrypted under a user-derived key (or the instance seal for instance secrets). Evidence: the credential record holds only salt, Argon2 parameters and the HKDF verifier (`encode_credential`, crates/riehub-identity/src/lib.rs:505). This plaintext layout is exactly what the card and docs/spec/identity.md section 2 prescribe, and it is a password hash equivalent, not a decryption key. The vault and its DEK stay AEAD sealed as before, the login unlocks it through slot `pw` (lib.rs:313). No new plaintext column or file holds a credential: the user record meta holds only email, display name, roles and auth kind (lib.rs:414), all plain by spec, identity.md section 1.
- [x] S1. No new plaintext column, file, cache or temp file can hold a credential or user content. Evidence: `stored_credential_never_contains_password` (crates/riehub-identity/tests/identity.rs:200) scans the stored credential bytes for the raw password and finds none. The privacy canary run in `canary_never_reaches_disk_or_logs` posts the canary as password to both new routes and scans the binary output for it. The password is wrapped in `Secret<String>` (crates/riehub-server/src/routes.rs:142) and never serialized.
- [x] S2. No log line, error message, metric label, trace attribute or audit field can carry a credential or user content. New types that hold them use `Secret<T>` or `Content`. Evidence: `invalid_login` (lib.rs:477) returns a fixed string. `password::validate` (crates/riehub-identity/src/password.rs:30) returns fixed strings. The new audit variants carry only `UserId`, `LoginFailReason` and `ThrottleScope` (crates/riehub-audit/src/event.rs:121, payload at event.rs:167). `InnerState` got a manual `Debug` that prints booleans only (crates/riehub-server/src/http.rs:28), `SetupResponse` and the identity `Service` are `missing_debug_implementations` (http.rs:348, lib.rs:95).
- [x] S9. Key material and plaintext secrets are zeroized on drop and never cloned into long-lived structures. Evidence: passwords travel as `Secret<String>` (riehub-core `Secret` zeroizes on drop), the Argon2 output is `Key32` and the verifier comparison copies into a stack array of fixed size. The `Service` holds no key material. The armored recovery key lives once in a `String` inside `SetupResponse` and leaves in the response body, this is the by-design single exposure. It is not zeroized, noted as an accepted residual in Findings.

## Findings

Low, no code change required to pass, reported to the maintainer:

1. Setup race. `setup_owner` checks `any_user()` (lib.rs:175) and then does two `Expect::New` puts. The unique index `records_lookup` blocks two concurrent setups with the same email, but two concurrent setups with different emails would both pass the check and both create an owner. The window is a one time bootstrap race and needs a locally racing client. Suggested fix for a later card: make the setup gate a single atomic step, for example a dedicated instance marker record with `Expect::New`.
2. The login IP throttle trusts the client supplied `x-forwarded-for` header (routes.rs:173). A caller can rotate that header to sidestep the 20 per IP limit. The 5 per account limit still holds and is header independent, so password guessing stays capped. Acceptable until a trusted proxy setting exists, worth a follow up when deploy hardening lands.
3. `stored_credential_never_contains_password` scans the fetched credential record data, not the whole sqlite database file as the card wording suggests. The password never enters any record, so the coverage is equivalent for the credential. The canary test covers the disk scan of the running binary for the password surface.
4. The canary covers the password surface but never reaches a successful setup, so the armored recovery key is not itself canary scanned. The key leaves only through `SetupResponse` (http.rs:349), which is the single allowed path, and no log or error path touches it.
5. The armored recovery key `String` is not zeroized after the response is built. One exposure by design, consistent with the card. `SetupResponse` has no `Debug` so it cannot leak through formatting.

Proof run during review: `cargo test -p riehub-identity` 11 passed, `cargo test -p riehub-server` all passed including the canary, `make rules` ok.

Verdict: pass
