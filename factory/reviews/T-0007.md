## Secrets and content

- [x] S1. Every new stored field that holds a credential or user content is encrypted under a user-derived key (or the instance seal for instance secrets). Evidence: n/a - the audit log stores only ids, enum strings, numbers, booleans and timestamps. No credential or user content is stored. Verified by `event_enum_has_no_string_fields` in crates/riehub-audit/src/event.rs, which walks every serialized string in every variant's JSON and asserts it is a typed id or a known enum value.
- [x] S1. No new plaintext column, file, cache or temp file can hold a credential or user content. Evidence: the audit table columns are seq, ts, kind, event (typed JSON) and mac (crates/riehub-store/src/sqlite.rs:744). The only new file is the audit key file in the data directory (crates/riehub-server/src/cli/mod.rs:16), which holds 32 random bytes, no user data.
- [x] S2. No log line, error message, metric label, trace attribute or audit field can carry a credential or user content. New types that hold them use `Secret<T>` or `Content`. CLI output prints seq, ts, kind, event JSON and mac hex only (crates/riehub-server/src/cli/mod.rs:245 to 252). `AuditChainMac` Debug prints `[audit-mac]` without key material (crates/riehub-audit/src/lib.rs:31).
- [x] S9. Key material and plaintext secrets are zeroized on drop and never cloned into long-lived structures. Evidence: the audit key lives in `Key32` (zeroizing type from riehub-crypto), behind an `Arc` so no byte copy is made on clone (crates/riehub-audit/src/lib.rs:19 to 21). Minor note in Findings: the temporary `bytes` Vec in `FileKeySource::load` (crates/riehub-server/src/cli/mod.rs:100) is not zeroized before drop. It is a short-lived read of the key file, the same bytes remain on disk in the 0600 file, so the exposure is no larger than the file itself. Acceptable, worth tightening when the coffer replaces this source in T-0102.

## Findings

1. Chain layout consistency: `chain_input` (crates/riehub-audit/src/log.rs:62 to 76) matches `mac_input` (crates/riehub-store/src/audit.rs:47 to 61) field for field: prev mac, seq LE, ts LE, kind bytes, event JSON bytes. Verified equal by reading both. The store computes `mac.compute(&prev, &input)` where `input` already starts with `prev`, so `AuditChainMac::compute` (crates/riehub-audit/src/lib.rs:50 to 55) prepends the prev mac a second time. Both append and verify do this identically, so the chain is self-consistent and all tamper tests pass, but the effective input is `prev_mac || prev_mac || seq || ts || kind || json`, one duplication more than the ADR 0010 formula `prev_mac || event`. Acceptable as an internal detail because both sides agree and the duplication adds no weakness, but the ADR text and the code do not match literally. If the layout ever changes, the format must be bumped once for both sides.
2. The card asks for a hand-written canonical encoder and `canonical_bytes` exists (crates/riehub-audit/src/event.rs:111, 234) with tests, but the mac actually runs over the store's JSON layout (`to_json` re-serialized by serde_json), not over `canonical_bytes`. Judged acceptable for now: the mac is still over a deterministic, code-fixed layout (serde_json serializes maps in insertion order, and `to_json` builds the map in fixed order with input-independent keys), so verification recomputes exactly what append stored, proven by the tamper tests and by `cli_verify_exits_3_on_tamper` against the real database. However, `canonical_bytes` is currently dead weight in the mac path and the spec section 6 table literally says `mac = hmac(audit_key, prev_mac || canonical_bytes(event))`. Either the mac should move to `canonical_bytes` in a later task or the spec line should be updated. Flagged for the maintainer, no fix requested in this review.
3. Key file handling is correct: `FileKeySource::ensure_file` creates with `create_new(true).mode(0o600)` (crates/riehub-server/src/cli/mod.rs:48 to 52) and refuses an existing file whose mode has any group or world bits (`mode() & 0o077 != 0`, cli/mod.rs:57 to 62). The key never lands in the database: the audit table stores only macs, and `audit_head` stores the head mac, not the key. Confirmed by reading the insert statements at crates/riehub-store/src/sqlite.rs:744 and 756.
4. Minor, no fix required: `verify.rs:31` computes `to + 1`, which would overflow panic at `to == u64::MAX` in a debug build. No caller passes `to` today and no route exposes it. Worth a `to.checked_add(1)` when `to` becomes user-reachable.
5. Minor: the temporary `bytes` Vec holding the raw key in `FileKeySource::load` is not zeroized (see S9 above). Tighten when T-0102 replaces the file source.

Verdict: pass
