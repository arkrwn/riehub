## Secrets and content

- [x] S1. Every new stored field that holds a credential or user content is encrypted under a user-derived key (or the instance seal for instance secrets). Evidence: the key record `data` holds only the verifier followed by the sealed label (`crates/riehub-identity/src/keys.rs:167-190`). The verifier is a KDF output, not the secret. The label is AEAD sealed under `hkdf(dek, "riehub/v1/label/key")` where the DEK comes from the unlocked vault (`keys.rs:115-119`), with the AAD binding user id and key id (`keys.rs:106-113`). The vault slot `hk.<ID>` holds the slot key sealed by the vault itself.
- [x] S1. No new plaintext column, file, cache or temp file can hold a credential or user content. Evidence: record `meta` holds user id, scopes, ACL prefixes and expiry only (`keys.rs:179-184`). The unlock cache holds only `Arc<Unlocked>` handles in memory (`crates/riehub-identity/src/session.rs:62-66`, `lib.rs:109`). The token never reaches a record (`KeyInfo` has no token field, `keys.rs:47-52`).
- [x] S2. No log line, error message, metric label, trace attribute or audit field can carry a credential or user content. New types that hold them use `Secret<T>` or `Content`. Evidence: all new error strings are static ("bad key token", "no such key", `keys.rs:316-347`). The access log fields are unchanged allowlisted fields (`http.rs:534-540`). `NewKey` and `AuthedKey` have no `Debug` impl (`keys.rs:56,66`). `NewKey.token` exists only in the create response body.
- [x] S9. Key material and plaintext secrets are zeroized on drop and never cloned into long-lived structures. Evidence: `hkdf` returns `Key32`, which zeroizes on drop (`crates/riehub-crypto/src/key.rs:24`). The vault slot key is stored sealed inside the vault. The cache holds `Arc<Unlocked>`, the same pattern the T-0104 review accepted. The raw `[u8; 32]` secret in `create_key` and `auth_key` drops without zeroize, the same pattern as the session secret in `session.rs`, no worse than the accepted T-0104 state.

## Access

- [x] S3. Every new route has a class in the route table (`public`, `self`, `admin_meta`, `key`) and a test for that class. No route returns another user's content or secrets to any role. Evidence: the four new routes carry classes in the table (`crates/riehub-server/src/routes.rs:150-177`), and `class_tests_cover_every_route` lists them (`crates/riehub-server/tests/admin_api.rs:141-144`). The list handler filters by the caller's own user id (`keys.rs:219`).
- [x] S4. Nothing new lets one principal obtain a session, hub key or unlock slot for another user. Evidence: `create_key` binds the record and the slot to the authenticated caller's user id (`keys.rs:152-190`), reached only through a session caller (`routes.rs` create_key rejects `CallerKind::HubKey`). No route accepts a target user id for key operations.
- [x] S5. Every new storage access for user-owned data takes a `UserScope`. There is a cross-user test that gets "not found". Evidence: `HubKey` records are `Owner::Instance` like sessions and are filtered by the authenticated caller (`keys.rs:219`, `keys.rs:267-269` returns `NotFound` on an owner mismatch). The owner check is real but a dedicated cross-user key test is not present, see Findings.
- [x] Authorization is checked on the server for every new action, not only hidden in the UI. Evidence: the class middleware enforces Key(scope) and Self_ (`http.rs:285-340`), the handlers re-check and reject hub keys for create and delete (`routes.rs`, `CallerKind::HubKey` guards in `create_key` and `delete_key`).

## Failure and input

Evidence: missing token is 401, wrong scope 403, bad verifier 401, expired 401 (`http.rs:286-308`, `keys.rs:313-365`). Tests: `key_without_scope_is_403`, `expired_key_is_401`, `revoked_key_is_401_within_one_request`. With no store, non-public classes get 503 (`http.rs:271-284`).
- [x] S7. Each new state change and each routed request writes an audit event with allowlisted fields only. Evidence: both `create_key` and `delete_key` write the vault, and `riehub-vault::save` appends the `vault.write` audit event with the new generation (`keys.rs:158,277`, `crates/riehub-identity/src/lib.rs:683-693`). Routed requests go through the unchanged access log. There is no dedicated key.create or key.delete event, the same pattern as session records, noted in Findings as an observation.
- [x] All new external input has size limits and is parsed with a typed parser. No string-built SQL, shell command or path. Evidence: the body goes through `read_json` with the global 32 MiB limit and typed `serde_json` field access (`routes.rs`, `read_json(req)` in `create_key`). Scopes parse through `KeyScope::parse`, unknown values are dropped and an empty list is refused (`routes.rs` create_key, `keys.rs:143-145`). No SQL, shell or path building anywhere in the diff.
- [x] S11. Every new outbound URL that a user can influence goes through the guarded HTTP client (SSRF rules). Evidence: n/a, the diff makes no outbound request.
- [x] Comparisons of secrets and tags are constant time. Evidence: the verifier comparison is `riehub_crypto::ct_eq` (`keys.rs:340`).
- [x] No new `unwrap`, `expect`, index or arithmetic can panic on external input. Evidence: `keys.rs` has no unwrap on input paths. The 32-byte slices are guarded (`data.len() >= 32` at `keys.rs:336`, `len > 32` at `keys.rs:299`). Token split uses `splitn(3, '_')` with a length check (`keys.rs:315-325`). `base64url_decode` returns an option and the array conversion is a checked `try_into`. In `routes.rs` the path tail uses `rsplit('/').next().unwrap_or("")`, which cannot panic. `duration_ms` uses `u64::try_from(...).unwrap_or(0)` (`http.rs:533`). The test file allows unwrap under `#![allow(...)]`, which is test-only.

## Findings

1. The Accept line `db_contents_cannot_rebuild_a_key` has no test. The session
task got `stolen_session_record_from_db_cannot_unlock`
(`crates/riehub-identity/tests/session.rs:96-126`), the key equivalent is
missing. A test that pulls the record `data`, tries the verifier as a slot
key and expects the unlock to fail would pin the property. This needs a code
change, reported to the maintainer.
2. Minor: `Service::key_label` (`keys.rs:287-307`) fetches the record by
lookup without an owner check. It fails closed, because the AAD binds the
caller's user id and the open returns an error for a foreign key, but the
error is `Error::Internal` rather than `NotFound`. No route calls it today.
3. Observation: the create and delete of the `HubKey` record write no
dedicated audit event beyond the `vault.write` from the vault save. This
matches the session pattern accepted in T-0104.
4. Observation: the card Build item 2 mentions `PATCH /api/v1/me/keys`, which
is not implemented. No Accept test requires it.
