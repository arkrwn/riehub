## Secrets and content

- [x] S1. Every new stored field that holds a credential or user content is encrypted under a user-derived key (or the instance seal for instance secrets). Evidence: the store treats user content as opaque bytes in `data` (record.rs:110, migrations/sqlite/0001_init.sql:18 `data BLOB`). The store never sees a key, encryption is the vault and crypto crates (later tasks). The record doc comment at record.rs:108 pins `data` as AEAD ciphertext for user-owned kinds.
- [x] S1. No new plaintext column, file, cache or temp file can hold a credential or user content. Evidence: 0001_init.sql defines only metadata columns (ids, enums, sort, timestamps, token and cost counters) plus the one `data BLOB`. `meta` must be a JSON object and the spec (storage.md section 2) restricts it to ids, enums, numbers, booleans and timestamps, enforced at the boundary by `record_to_row` (sqlite.rs:139).
- [x] S2. No log line, error message, metric label, trace attribute or audit field can carry a credential or user content. New types that hold them use `Secret<T>` or `Content`. Evidence: `sqlite_error` (sqlite.rs:111-122) never propagates a driver message, it maps to `Error::Conflict` or `Error::Internal(None)`. The crate has no logging at all. `AuditDraft` (audit.rs:8-12) carries typed metadata fields only, and `UsageRow` (usage.rs:8-21) is metadata only.
- [x] S9. Key material and plaintext secrets are zeroized on drop and never cloned into long-lived structures. Evidence: n/a, the store handles no key material and no plaintext secret. The only bytes it holds are opaque ciphertext blobs and chain macs, which are not secrets under S9. `Secret<T>` usage arrives with the vault and audit tasks that own keys.

## Access

- [x] S3. Every new route has a class in the route table (`public`, `self`, `admin_meta`, `key`) and a test for that class. No route returns another user's content or secrets to any role. Evidence: n/a, this change adds no HTTP route. `riehub-server` does not exist yet and the card paths are `crates/riehub-store/` only.
- [x] S4. Nothing new lets one principal obtain a session, hub key or unlock slot for another user. Evidence: n/a, the store only persists what callers give it, it issues nothing.
- [x] S5. Every new storage access for user-owned data takes a `UserScope`. There is a cross-user test that gets "not found". Evidence: every record method of the trait takes `&Owner` as its first argument (lib.rs:25-41) and every SQL statement in sqlite.rs filters `WHERE owner = ?` bound from that argument (GET_SQL sqlite.rs:193, GET_BY_LOOKUP_SQL sqlite.rs:194, delete sqlite.rs:326, list sqlite.rs:346-349, delete_owner sqlite.rs:395). Cross-owner invisibility is proven by conformance cases `case_get_other_owner` (conformance.rs:189), `case_list_owners` (conformance.rs:205) and `case_delete_owner` (conformance.rs:357). `owner_from_str` (sqlite.rs:33) rejects malformed owner keys, so a wrong owner cannot alias to another.
- [x] Authorization is checked on the server for every new action, not only hidden in the UI. Evidence: n/a, no server or UI in this change. The trait forces the owner into the query itself, so the server layer cannot forget the tenant filter when it calls the store.

## Failure and input

- [x] S6. Each new check (auth, limit, budget, masking, guardrail, audit write) fails closed, and there is a test for the failure path. Evidence: every method returns `Result` and errors are mapped, never swallowed. `audit_append` fails closed on an empty batch (sqlite.rs:404) and rolls back the whole batch on any error inside the chain (sqlite.rs:410-419). `migrate` refuses a schema newer than the build knows (sqlite.rs:670-674, test `newer_schema_is_refused`). `put` conflicts on a version mismatch (sqlite.rs:278-282, case `case_put_wrong_version_conflicts`) and on a duplicate id or lookup (case `case_put_new_twice_conflicts`, `case_lookup_unique`).
- [x] S7. Each new state change and each routed request writes an audit event with allowlisted fields only. Evidence: the store provides `audit_append` with the one serialized chain (sqlite.rs:403-420, 715-768) and the `AuditDraft` shape is typed metadata only (audit.rs:8-12). The routing tasks that write events come later and will be reviewed there. `case_audit_gapless` (conformance.rs:474) proves gapless seq and verifiable macs under 10 concurrent writers.
- [x] All new external input has size limits and is parsed with a typed parser. No string-built SQL, shell command or path. Evidence: `Kind` is a closed enum with a strict parser (record.rs:41-57), owners parse through `UserId::parse` (sqlite.rs:33-42), `meta` must be a JSON object (sqlite.rs:139), `usage_query.group_by` is a fixed enum (usage.rs:26-36). Every value in every query is bound. The two dynamic SQL builders are safe: `list` uses `QueryBuilder` with `push_bind` for every value (sqlite.rs:344-370) and only pushes literal fragments, and `audit_read` (sqlite.rs:430-441) plus `usage_query` (sqlite.rs:544-590) build strings only from code constants and bind all values. Size limits are the caller's job at the typed trait boundary, n/a here.
- [x] S11. Every new outbound URL that a user can influence goes through the guarded HTTP client (SSRF rules). Evidence: n/a, the crate makes no HTTP request. The only network resource is the local database file.
- [x] Comparisons of secrets and tags are constant time. Evidence: n/a, the crate compares no secret. The lease holder comparison (sqlite.rs:645) compares scheduler labels, not credentials.
- [x] No new `unwrap`, `expect`, index or arithmetic can panic on external input. Evidence: the workspace denies clippy `unwrap_used`, `expect_used` and `panic` (Cargo.toml:16-22). All non-test code uses `map_err` (for example sqlite.rs:205, 376, 452). The only allows are `#![allow(clippy::unwrap_used, clippy::expect_used)]` at conformance.rs:6 and in the `#[cfg(test)]` module at sqlite.rs:772, both test-only. `row_to_record` clamps negative versions with `max(0)` (sqlite.rs:184) and `usage_query` rejects an empty group_by (sqlite.rs:539). `make rules` passes.

## Transport and platform

- [x] S8. New cookies, headers and TLS settings follow the spec. Evidence: n/a, no transport surface in this change. sqlx is opened with `default-features = false` and no TLS feature (Cargo.toml), which matches the card's "tls-rustls off" for a local file database.
- [x] S10. New dependencies are named by the card or the spec, are maintained, and pass `cargo deny check` or `npm audit`. List them: `sqlx 0.9` with features `sqlite` and `runtime-tokio`, `default-features = false`, named by the card, bundled SQLite confirmed by `libsqlite3-sys` with `cc` in Cargo.lock. `serde_json` is required by the spec's JSON `meta` and audit event fields. `tokio` is a dev-dependency for the async tests. `async-trait` is not named literally in the card, but the spec (storage.md section 3) defines `trait Store` with async methods on a `Send + Sync + 'static` object, which needs it. It is a small, widely used proc-macro crate with no runtime security surface, so it is acceptable. `make security` and the gate cover the deny checks.
- [x] S12. No telemetry, no third-party origin, no call home. Evidence: the crate contains no network client, no HTTP call and no telemetry of any kind, only the local SQLite file through sqlx.
- [x] No `unsafe`, no Windows code path. Evidence: `#![forbid(unsafe_code)]` at lib.rs:3 and the workspace sets `unsafe_code = "forbid"` (Cargo.toml:13). No `cfg(windows)` or `cfg(target_os = "windows")` anywhere. The single `cfg(not(unix))` branch (sqlite.rs:106-109) is a no-op stub for the file-mode check, not Windows-specific logic, and the crate otherwise fails to build nothing on non-unix. Unix-only permission code is behind `cfg(unix)`.
- [x] R1. No AI signature or mark in the diff or in any commit of the branch, and no co-author trailer. Evidence: `git log main..HEAD --format=%B` shows exactly one line, `feat: add the store trait and the sqlite backend`, with no trailer and no mark. No code comment names a tool.

## Findings

No blocking finding. Two notes for later tasks, no fix needed now:

- `refuses_world_readable_db` covers the 0644 case, the check itself refuses any mode with group or world bits (sqlite.rs:93), which is the stronger rule from the card.
- The sqlite backend never truncates or rotates the WAL and shm files next to the database, their modes follow the process umask after creation. This matches SQLite's normal behaviour and the file is created 0600 first, but the deploy task should confirm the data directory is 0700 so WAL sidecars stay private.

Verdict: pass
