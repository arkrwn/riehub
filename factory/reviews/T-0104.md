## Secrets and content

- [x] S1. Every new stored field that holds a credential or user content is encrypted under a user-derived key (or the instance seal for instance secrets). Evidence: the session record stores only the verifier `hkdf(secret, riehub/v1/token/auth)` in `data` and plain ids and timestamps in `meta` (crates/riehub-identity/src/session.rs:380 to 407, `session_record`). This is exactly what docs/spec/security.md section 3.2 prescribes. The secret itself never lands in the store, it lives only in the cookie token. The vault slot `ws.<SID>` holds the slot key wrapped under the user's DEK (`add_slot`, session.rs:96 to 102). The cookie key is an instance secret sealed in the instance coffer (`COOKIE_KEY_PATH`, crates/riehub-vault/src/instance.rs:28).
- [x] S1. No new plaintext column, file, cache or temp file can hold a credential or user content. Evidence: the session record `data` is the verifier, not the secret. The unlock cache (session.rs:50 to 53) holds `Arc<Unlocked>` vault keys in memory only, it is a `HashMap` inside the `Service`, never written to the store, and no code path serializes it. `stolen_session_record_from_db_cannot_unlock` (crates/riehub-identity/tests/session.rs:91) proves the stored verifier alone cannot open the vault.
- [x] S2. No log line, error message, metric label, trace attribute or audit field can carry a credential or user content. New types that hold them use `Secret<T>` or `Content`. Evidence: the token and the session secret never appear in any log or error. Unauthorized errors return fixed strings (session.rs:229, 233, 235, 246, 251, 254). `Session` and `AuthedSession` and `CacheEntry` are `missing_debug_implementations` so the token cannot leak through Debug (session.rs:27, 41, 49). The access log logs only request id, method, route template, status and duration (crates/riehub-server/src/http.rs:374 to 381). The session routes return user id, session id and csrf only (crates/riehub-server/src/routes.rs:197 to 204, 236 to 249). `SessionInfo` serializes ids and timestamps only (session.rs:371 to 378).
- [x] S9. Key material and plaintext secrets are zeroized on drop and never cloned into long-lived structures. Evidence: the token secret is a stack `[u8; 32]` (session.rs:237 to 240), the slot key is a `Key32` (zeroizing) and the verifier a fixed array. `Unlocked` vault keys live only inside the bounded unlock cache and are dropped by eviction, logout (`end_session`, session.rs:215 to 218) and timeout (`delete_session_record`, session.rs:362 to 366). The cache is capped at 10 000 entries and idle evicted after 10 minutes (session.rs:337 to 351, `UNLOCK_CACHE_IDLE`, `UNLOCK_CACHE_MAX`). Residual: the token `String` itself is a plain `String` in `Session` and in the cookie, like every token string in this codebase so far, noted in Findings.

## Access

- [x] S3. Every new route has a class in the route table (`public`, `self`, `admin_meta`, `key`) and a test for that class. No route returns another user's content or secrets to any role. Evidence: `GET /api/v1/me`, `POST /api/v1/auth/logout`, `GET /api/v1/me/sessions` and `DELETE /api/v1/me/sessions/{id}` are all `RouteClass::Self_` in the table (crates/riehub-server/src/routes.rs:80 to 108). All four are exercised over the real binary in crates/riehub-server/tests/sessions_api.rs. Every one resolves the user from the validated session token, never from request text, so no route returns another user's data.
- [x] S4. Nothing new lets one principal obtain a session, hub key or unlock slot for another user. Evidence: a session is created only inside `login` after the caller's own password matched (crates/riehub-identity/src/lib.rs:335 to 338). No route takes a user id. A session validates only when the presented secret hashes to the stored verifier (`ct_eq`, session.rs:252 to 255). `stolen_session_record_from_db_cannot_unlock` proves the verifier does not yield the slot key, because slot and verifier use different HKDF info strings (`token/slot` vs `token/auth`, session.rs:14 to 15, 60 to 66).
- [x] S5. Every new storage access for user-owned data takes a `UserScope`. There is a cross-user test that gets "not found". Evidence: session records live under `Owner::Instance` with the user id in `meta` by design (identity spec section 3, any node must serve the session, proven by `session_works_on_a_second_server_instance_sharing_the_store`). The vault access is always under the user id resolved from the validated token (session.rs:280 to 282, 317 to 322), never from caller text. The end route checks ownership against `list_sessions(&session.user_id)` and returns 404 when not owned, failing closed with `unwrap_or_default` on the list error (routes.rs:263 to 274). A dedicated cross-user 404 test is deferred to T-0105 (`owner_gets_404_for_another_users_session_id`), the ownership gate already exists here.
- [x] Authorization is checked on the server for every new action, not only hidden in the UI. Evidence: all four routes sit behind the route table middleware. The CSRF gate is a server middleware on mutating `/api` requests (http.rs:228 to 252). Ownership of an ended session is checked in the handler (routes.rs:263 to 274). No UI exists yet.

## Findings

Observed once during review, not reproducible after: the first full
`cargo test -p riehub-identity` run failed `login_is_throttled_after_5_failures`
and `login_after_throttle_lets_a_correct_password_through_after_window`,
four later runs of the same suite passed. Likely cause: `count_failure`
swallows store errors with `let _ =` (crates/riehub-identity/src/lib.rs:169
to 178), so a transient store error under load drops a throttle count
and the limit is not reached. Worth hardening.

Open items, none blocks this task:

1. `assemble` in crates/riehub-server/src/serve.rs:54 to 57 falls back
   to an all zero cookie key when the coffer entry has a length other
   than 32, while the audit key path errors out at serve.rs:63 to 67.
   A wrong length cookie key should refuse to start too.
2. The csrf header compare (crates/riehub-server/src/http.rs:242) is
   not constant time. The compared value is `hmac(cookie_key, sid)` and
   the key never leaves the server, so the practical risk is low.
3. Logout and `DELETE /api/v1/me/sessions/{id}` write no audit event,
   the audit enum has no session action yet. Security spec section 7
   and S7 point at this for a later task.
4. Unlock cache idle eviction runs only on insert (session.rs:326), so
   an entry idle past 10 minutes lingers in memory until the next
   cache miss. The cap and the on-revoke removal are correct.
5. If storing the session record fails after the vault slot was saved,
   slot `ws.<SID>` stays as an orphan. Identity spec section 3 already
   says stale slots are cleaned on the next login.

green (sessions_api 6 passed, identity_api 6 passed, privacy_canary
