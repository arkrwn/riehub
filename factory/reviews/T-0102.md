## Findings

F1 (must fix before merge, code fix required). `FileHostSeal::unseal` ignores the blob parameter entirely (`crates/riehub-vault/src/instance.rs:134`), so the `instance.host-key` record is dead weight for the file backend. I reproduced this outside the test suite: I ran `riehub init`, set the record data to `X'00'` with a direct sqlite write, and `riehub serve` still started and ran (timeout killed it after 10 s on a free port). The acceptance test `serve_fails_closed_when_host_key_is_missing_or_wrong` only passes because it binds `127.0.0.1:8080`, and port 8080 is already in use on this machine (`ss -tln` shows a listener), so serve exits with "the bind address is not usable". On a host with a free port 8080 the test would hang or fail. Two fixes are needed. First, `FileHostSeal::unseal` should reject a non-empty blob with `SealError::Invalid` so the record is bound to the backend and a tampered record fails closed. Second, the test should bind a free port (for example 127.0.0.1:0 with the actual port printed, or a probed port like `tests/common/mod.rs` does) so it stops depending on the host environment. Security impact of the current code is limited: an attacker who can write the database still cannot open the coffer without the key file, so S1 holds, but the fail closed property the test claims is not actually implemented for the file backend.

F2 (minor, no invariant broken). The host key bytes in `create` (`instance.rs:184`) and the `[u8; 32]` returned by `HostSeal::unseal` (`instance.rs:273`) are plain arrays, not `Zeroizing`. The return type is fixed by the cofferak `HostSeal` trait, and the values are short lived locals, so this matches the existing per-user vault code. Noted for the record, no action required for this task.
