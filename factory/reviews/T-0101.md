## Findings

Nothing fixed during the review, no code change needed. Three
observations, none of them a card violation:

1. `recover` (`crates/riehub-vault/src/lib.rs:153-166`) verifies the
   file with `verify(&dek, None)` and takes no audit anchor, so the
   rollback refusal does not apply on the recovery path. This matches
   the card and the spec 3.3 signature, where `recover` has no audit
   parameter. When the server wires recovery (T-0102 or later), it
   should either anchor recovery the same way as `unlock` or document
   why the recovery path is exempt.
2. `save` (`crates/riehub-vault/src/lib.rs:406-410`) puts the record
   first and appends `vault.write` after the put succeeds. If the audit
   write fails, the store already holds the new generation but no audit
   event exists, so the rollback anchor lags one generation and the
   write is unaudited (S6/S7). Writing the audit event before the put,
   or compensating by removing the record, would close this. The
   current code does surface the error to the caller.
3. `riehub-audit` is declared as a dev-dependency of `riehub-vault`
   (`crates/riehub-vault/Cargo.toml:15-16`) but no test uses it. It can
   be dropped, or kept if the audit wiring test is planned next.

Verdict: pass
