## Secrets and content

- [x] S1. Every new stored field that holds a credential or user content is encrypted under a user-derived key (or the instance seal for instance secrets). Evidence: the invite record stores only `invite_hash` (an HMAC of the token, crates/riehub-identity/src/invite.rs:83) and `invite_expires_at` (invite.rs:84), never the token. The vault created at accept is the existing encrypted path (`riehub_vault::create` and `riehub_vault::save`, invite.rs:177 to 179). The credential record holds salt, Argon2 parameters and the `hkdf` verifier only (invite.rs:183 to 205, pre-existing T-0103 pattern, the password itself never lands in the store). The armored recovery key exists only in the response body, it is never stored (invite.rs:180, 231).
- [x] S1. No new plaintext column, file, cache or temp file can hold a credential or user content. Evidence: the new stored meta fields are `display_name`, `roles`, `invite_hash`, `invite_expires_at`, all plain per identity spec section 1 (display_name is plain, at most 80 characters, invite.rs:66). `roles` are plain role strings by design (identity spec section 5). The admin list response carries ids, emails, names, statuses, roles only (routes.rs:365 to 372), pinned by `admin_user_list_has_no_secret_or_content_fields`.
- [x] S2. No log line, error message, metric label, trace attribute or audit field can carry a credential or user content. New types that hold them use `Secret<T>` or `Content`. Evidence: the invite token and the password never appear in any error string, the errors are fixed text ("no such invite", "this invite has expired", invite.rs:111, 115). The password is wrapped in `Secret<String>` (invite.rs:158, routes.rs:549). The access log still logs only request id, method, template, status, duration (http.rs:454 to 460). The audit event written at accept carries the user id only (invite.rs:220 to 229). The recovery key response type `SetupResponse` has no Debug (http.rs:493).
- [x] S9. Key material and plaintext secrets are zeroized on drop and never cloned into long-lived structures. Evidence: the invite token is a stack `random_bytes::<32>` hex encoded, the raw bytes drop at the end of `create_invite` (invite.rs:58 to 61). The password is `Secret<String>` (zeroizing). The vault keys live inside `Unlocked` and the pre-existing unlock cache, unchanged here. The recovery key armored string is a transient `String` returned once, noted in Findings as the same residual token-string pattern as T-0104.

## Findings

Must fix before this task is done:

1. FIXED. Role assignment is owner-only in the spec, an admin could
   grant the owner role. The fix adds an owner-only guard at the top
   of `patch_user` (crates/riehub-identity/src/admin.rs:31 to 42):
   when the patch body carries any role that parses to `owner` and the
   caller is not an owner, the answer is 403 "only an owner assigns
   the owner role". `Role::parse` is exact match (roles.rs:27 to 34),
   so no spelling variant bypasses the guard, and the guard runs
   before any store write. Pinned by `admin_cannot_grant_the_owner_role`
   (tests/admin_api.rs:364): the owner promotes the member to admin,
   the admin then PATCHes their own roles to `["owner"]` and gets 403.

2. FIXED. Disabling a user did not end their sessions. The fix sweeps
   the target's sessions inside `patch_user` when the new status is
   `disabled` (crates/riehub-identity/src/admin.rs:115 to 123), so no
   live session survives the disable. Login already refuses a disabled
   user (lib.rs:319), so the only way back in is closed too. Pinned
   end to end by `disabling_a_user_ends_their_sessions`
   (tests/admin_api.rs:418): after the disable PATCH, the member's
   `/api/v1/me` call with the old cookie answers 401. Note:
   `validate_session` itself still reads no user record (session.rs:238
   to 316), the sweep plus the login check is what closes the gap, see
   open item 8.

Open items, none blocks this task on its own:

3. Handlers `admin_create_user` (routes.rs:400), `admin_create_invite`
   (routes.rs:477) and `admin_audit` (routes.rs:502) discard the
   `require_session` result with `let _ =` and rely solely on the
   middleware. The other admin handlers match on the result
   (routes.rs:353, 432, 462). Defense in depth: match on the result
   there too, so the handler refuses when the middleware is ever
   reordered or bypassed.
4. S7 gap: `patch_user`, `delete_user` and `create_invite` write no
   audit event, the audit enum has no user update, user delete or
   invite create action. Same class as the T-0104 session action gap.
5. `delete_user` ignores per-session deletion errors with `let _ =`
   (admin.rs:157 to 164), so a store error can leave ghost session
   records. Harmless, the user record is already gone and
   `validate_session` would fail on the missing user roles path.
6. `invite_hash` is an HMAC with an all-zero fixed key
   (invite.rs:19), in effect an unkeyed hash. With a 256 bit random
   token this is not brute forceable, but a real instance key from the
   coffer would be cleaner.
7. `GET/POST /api/v1/invites/{token}` are unauthenticated and each
   attempt scans all pending users (invite.rs:97 to 136), with no rate
   limit. Brute force is infeasible, but the scan is a cheap unauthenticated
   store load. A small rate limit would close it.
8. `validate_session` never consults the user record status, it trusts
   the session record alone (session.rs:238 to 316). The disable sweep
   in `patch_user` closes the live gap, but any future path that mints
   or keeps a session for a disabled user would leak. The
   `user_record_status` helper (lib.rs:375 to 381) exists for exactly
   this check and is currently unused. Defense in depth: read the
   user status inside `validate_session` and answer 401 for a
   non-active user.
