# AGENTS.md

Instructions for AI coding agents working in this repository, whatever
the tool or vendor. `CLAUDE.md` is a symlink to this file. Other tools
that look for their own file name (`GEMINI.md`, `.cursorrules`) should be
pointed here the same way, not given a separate copy.

This file is written so that a small model can follow it step by step.
Do exactly what it says. When it does not cover a case, stop and ask.

## 1. The goal

Build **riehub** from version `0.0.1` to a release candidate for `1.0.0`
by finishing every task card in `factory/tasks/`, in order, one branch
per task.

riehub is a self-hosted, multi-user AI hub: one private router for every
AI model, plus each user's own connections, MCP connectors, skills and
workflows. Security comes before every other goal, including features
and speed. The server is Rust. Only the web UI in `web/` is TypeScript.
It runs on Linux and macOS. It never supports Windows.

You are done when `factory/factory.sh next` prints `DONE` or `STOP`.
Then report to the maintainer. Tagging `1.0.0` is a human decision.

## 2. The loop

Repeat these steps. Do not skip one and do not add your own.

1. Run `factory/factory.sh next`. It prints one task card, or `DONE`, or
   `STOP`. On `DONE` or `STOP`, write a short report and end.
2. Read the card. Then read only the spec sections and ADRs the card
   lists under `Spec:`. Do not read the whole `docs/` tree.
3. Run `factory/factory.sh start <ID>`. It creates the branch.
4. Build what the card says, inside the paths the card lists. Write each
   test named under `Accept` first, watch it fail, then make it pass.
   While working, run only the narrow command under `Proof`
   (for example `cargo test -p riehub-vault`), not the whole gate.
5. Update the docs the card names. Add one line to `CHANGELOG.md` under
   `Unreleased` for a `feat` or `fix` task.
6. If the card says `Review: security`, do the review in section 5.
7. Commit (message rules in R1 and section 8). Then run
   `factory/factory.sh gate`. It prints `GATE GREEN` or the failing tail.
8. Gate red: fix the cause, commit, run the gate again. You get **three**
   fix attempts per task. After the third red gate run
   `factory/factory.sh block <ID> "<one line: what fails and why>"` and
   go to step 1. Never weaken, delete or skip a test to get green.
9. Gate green: run `factory/factory.sh finish <ID>`. It checks the
   proof, merges to `main`, deletes the branch and prints the next task.
10. Go to step 1.

`factory/factory.sh status` shows where things stand at any time. If a
session ends in the middle of a task, the next session runs
`factory/factory.sh next` and it says `Resume`.

## 3. Bootstrap, once

Only when `git log` says there are no commits yet:

1. Check `git config user.name` and `git config user.email`. If either
   is empty, stop and ask the maintainer to set them.
2. Run `make check && make docs`. Both must be green.
3. `git add -A && git commit -m "chore: project skeleton"` on `main`.
   This is the only commit ever made directly on `main` by hand.
4. Run `git ls-remote origin`. If it answers and lists no `main`
   branch, run `git push -u origin main`. This is the only push to
   `main` ever made by hand. If it fails with a permission error, do
   not retry: the factory then works in local mode, say so in your
   report.
5. Run `factory/factory.sh status`. The first line says `mode: pr` or
   `mode: local`. Continue with the loop.

## 4. Rules that are never optional

- **R1. No AI signature or mark of any kind, anywhere.** This is
  strict. No co-author trailer at all, no "generated with" or
  "generated by" line, no robot emoji, no tool name as a signature, no
  "assisted by" note. It applies to commit messages, the commit author
  and committer identity, pull request titles and bodies, comments on
  pull requests and issues, code comments, file headers, docs, review
  files and UI text. Your tool may add such a line by default: turn it
  off, and read every commit message before you commit. Commits are
  made under the maintainer's configured git identity, never under a
  tool's name. `make rules` and `factory.sh finish` reject a violation.
  Naming a product as a subject is fine, for example "add the Claude
  Code agent module". Signing work with it is not.
- **R2. One task, one branch, through the factory.** Never commit on
  `main` by hand after the bootstrap. Never push to `main` after the
  bootstrap push. Never edit
  `factory/state.tsv` or `docs/PROGRESS.md` by hand, `finish` writes
  them. Never run `factory/factory.sh approve`, it belongs to the
  maintainer.
- **R3. No secrets in the repository.** No `.env` files, keys, tokens,
  credentials, databases or personal infrastructure details, not in
  code, tests, docs or commit messages. Test credentials are obvious
  fakes built in code, for example `format!("sk-{}", "test".repeat(8))`.
- **R4. The security invariants hold in every commit.** They are S1 to
  S12 in [`docs/SPEC.md`](docs/SPEC.md), section 2. If a task seems to
  need breaking one, stop and block the task. Do not decide alone.
- **R5. The plan is fixed.** Do not reorder, merge, split or invent
  tasks. Do not re-argue an ADR. If the plan is wrong, block the task
  with the reason and let the maintainer decide.
- **R6. Stay inside the card.** Touch only the paths the card lists,
  plus `CHANGELOG.md`, `mkdocs.yml` and the docs it names. No drive-by
  refactors. No new dependency unless the card or the spec names it. A
  dependency you believe is needed but is not named: block and ask.
- **R7. Tests pin behaviour.** Every `Accept` line is a test that exists
  and passes. A test that cannot fail is not a test.
- **R8. Proof, not hope.** Never say something works without the
  command and its real exit code. "Should pass" is not proof.
- **R9. Platform.** Rust for everything except `web/`. Linux and macOS
  only. No Windows code path, not even behind a `cfg`.
- **R10. Docs move with the code.** A new page is added to the `nav` in
  `mkdocs.yml`. A real trade-off that no ADR covers gets a new ADR.

## 5. Security review (cards marked `Review: security`)

Before the gate, copy `factory/SECURITY-CHECKLIST.md` to
`factory/reviews/<ID>.md` and answer every item with evidence: a file
and line, or a test name. An item that does not apply gets `n/a` and
one reason. Tick the box only when the evidence is real. End the file
with the single line `Verdict: pass`. If any item fails, fix the code
first.

If your tool can start sub-agents, give this review to a fresh one. Its
whole brief is: the output of `git diff main...HEAD`, the checklist
file, and `docs/SPEC.md` section 2. A reviewer that did not write the
code finds more.

## 6. Spending tokens well

- Read a file only when you need it. Read the part, not the whole.
- The card and its `Spec:` links are the context for a task. The other
  cards and the other spec pages are not.
- Never read `Cargo.lock`, `web/package-lock.json`, `target/`,
  `node_modules/`, `site/` or the gate log beyond its tail.
- Run narrow tests while you work. Run `factory/factory.sh gate` once
  when you believe the task is finished, not after every edit.
- Use a sub-agent only for the security review in section 5, or to
  search code you have not seen. Never to do the task itself in
  parallel, and never more than one at a time.
- Do not restate the plan, the card or your past steps in your answers.
  Report in five lines or fewer per finished task.
- The same error twice with the same fix means the fix is wrong. Stop,
  read the error again, and change approach. Three red gates is the
  limit (step 8).

## 8. Writing style

Applies to everything a person reads: docs, code comments, UI text,
CLI output, log messages, commit messages, pull request text, review
files and your own reports. These two rules are strict. `make rules`
and `factory.sh finish` reject a violation.

- **No em-dash, anywhere, ever.** Not in any file of any type. Where
  you would use one, use a plain hyphen with spaces ( - ) or start a
  new sentence.
- **No semicolon in prose.** To separate ideas inside a paragraph use
  a comma, or split the sentence. Semicolons belong to code only.
- Plain, short sentences. Say what is true and how you know.
- Commit messages are conventional: `feat:`, `fix:`, `docs:`, `chore:`,
  `test:`, `refactor:`. One line, lower case, no trailing period.
- Diagrams are mermaid blocks inside the page.
- Links between pages under `docs/` are relative. Links from `docs/` to
  files outside it (`SDD.md`, `AGENTS.md`, `factory/`, source files) use
  the full GitHub URL, otherwise the strict docs build fails.

  docs/
    SPEC.md            # the contract: scope, invariants S1-S12, architecture

    PROGRESS.md        # generated status table with proof
  scripts/             # rules-lint.sh, security.sh, install-tools.sh

    riehub-governance  #   budgets, limits, teams, masking, guardrails
    riehub-mcp         #   MCP client, gateway, connectors
    riehub-automation  #   skills, chat sessions, workflows

  deploy/              # Docker, Helm, systemd, launchd (version 0.8.0)
